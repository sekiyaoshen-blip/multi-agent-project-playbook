# Contributing

Keep this skill focused on initializing or simplifying project collaboration.
Preserve durable module ownership, direct routing, one cross-module lead, and
native-first execution. Do not reintroduce model routing or mandatory ceremony.

Before adding a rule or template, identify the concrete failure it prevents and
why existing native tools or project instructions are insufficient. Keep
conditional detail out of the default startup context. Supply complete Chinese
versions of user-facing prompts.

For documentation changes, check frontmatter/YAML, affected template/skeleton
consistency, links, and Markdown fences. Preserve explicit-only invocation.
Regenerate the existing package manifest when contents change; its packaging
checksums are not a requirement for projects using the skill.

## Update Sequence

For an authorized maintenance update: validate the source change, commit and
push it to the configured GitHub repository, sync the changed files into the
local skill, then update the skill-managed rules in already-adopted local
projects within the user's established scope. Preserve local customizations,
project-specific rules, and unrelated changes. Commit only the project rule
changes; project pushes follow their own repository policy. Do not include
unrelated unpublished history merely to push a rule update.

Include development worktrees in that scope; exclude frozen verification/release
snapshots. Do not initialize unadopted projects, edit historical evidence, or
interrupt running tasks for a routine rule update. Updated files do not prove
that an active task has reloaded them. Report each sync result and any remaining
failure separately; a failed stage must not be described as fully synchronized.

This is the completion sequence when maintaining the skill, not a background
updater or permission to broaden a standalone installation request.
